## 项目自身发现的问题

### 1. `browser` 只是标签，不是已经实现的能力

`sites.json` 给 Beauty Independent、Beauty Packaging、HAPPI 和亿邦动力配了 `crawl_strategy=browser`，但当前执行引擎注册表只有：

- `static_http`
- `feed_direct`
- `sitemap_http`
- `json_api`
- `provider_api`

`discovery_method=html` 仍会解析成 `static_http`。因此这些来源过去没有被真正的浏览器引擎验收过；亿邦动力的成功也只是静态 HTTP 成功。以后能力表必须由实际 `execution_engine` 和成功运行证据生成，不能由意图标签推断。

### 2. robots 状态处理过于粗糙

当前程序只接受 robots 的 200/404，403 直接报 `robots_unavailable`。RFC 9309 区分：

- 4xx 是 robots “unavailable”，协议允许客户端自行决定是否访问；
- 5xx/网络错误是 “unreachable”，应暂按完全禁止；
- 200 且规则命中 `Disallow` 才是明确的规则停爬。

项目可以选择比 RFC 更保守，但数据库必须分别保存 `explicit_disallow`、`robots_4xx`、`robots_5xx`、`network_error` 和 `challenge_page`，不能都叫“robots 禁止”。参考：[RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html)。

### 3. 来源状态缺少自动过期

Premium Beauty News 的维护页被固化成长期结论，而 CosmeticsDesign 又因历史文章仍可访问被短暂误判为恢复。建议为探测结论增加：

- `observed_at`
- `evidence_url`
- `http_status`
- `content_signature`
- `expires_at`
- `next_probe_at`

`maintenance`、`old_route`、`waf_challenge` 应自动复测；只有明确条款/robots 禁止才长期停爬。

## 可复用的网站资讯采集方法

### 新信源标准流程

1. **身份登记**：用稳定 `catalog_id` 识别来源，入口 URL 可变，来源身份不变。
2. **合规探测**：读取 robots、站点条款、登录/付费边界和内容使用信号；先决定可采范围，再选技术。
3. **入口发现**：按 `官方 API → RSS/Atom → Sitemap → 静态栏目 HTML → 普通 JS 浏览器` 的顺序选择。Atom 本来就是面向网页内容分发的标准格式，见 [RFC 4287](https://www.rfc-editor.org/rfc/rfc4287/)。
4. **分层验证**：分别验证列表发现、文章抓取、正文抽取、发布时间、标签/广告证据；不要用“首页 200”代表全文链路成功。
5. **小流量 canary**：每站先取 1 个列表页和 1 篇公开文章，保存响应状态、最终 URL、内容类型、页面签名和快照。
6. **日期闭合**：日报按来源时区的发布日期筛选，分页直到越过目标日；目标日无稿是健康空结果。
7. **增量与去重**：Feed 使用 GUID/Atom ID，Sitemap 使用 URL+`lastmod`，网页使用 canonical URL+内容哈希；发送 ETag/If-Modified-Since 条件请求。HTTP 条件请求见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)。
8. **逐级降级**：正文不可取时可按许可降为标题、日期、短摘和原文链接；登录、付费、验证码和明确禁止不是可自动降级绕过的技术问题。
9. **回归固化**：成功页面脱敏保存为 fixture；结构漂移先在 fixture 上修解析器，再做单站 canary。
10. **稳定性验收**：单次成功只叫“已打通”；至少跨 3 个发布周期成功、无重复和漏日，才能叫“稳定”。

### Sitemap 的正确用途

Sitemap 主要解决 URL 发现，不保证内容可抓，也不保证 `lastmod` 是文章发布时间。Sitemap index 需要先展开子 Sitemap；`lastmod` 可以帮助增量拉取子文件，但文章仍要从页面或 API 校验发布日期。参考：[Sitemaps 协议](https://www.sitemaps.org/protocol.html)。

### 浏览器引擎的边界

浏览器引擎适合：正常 JavaScript 渲染、客户端路由、页面内 JSON 状态。它不用于：自动解 CAPTCHA、伪造登录、隐藏机器人身份、绕过付费墙或明确的 robots/条款限制。若站点持续对具名低频采集器发挑战，应改走授权 Feed/API 或替换信源。

## 推荐实施顺序

1. 观察 Premium Beauty News 至少 3 个发布周期，再决定是否提高单轮处理上限并标记稳定。
2. 保持 CosmeticsDesign 关闭状态；若需要替代，再独立评估 NutraIngredients Beauty & Wellness，不能沿用旧来源身份。
3. 修正 robots 结果分类和探测状态过期机制，避免以后再次把临时故障写成永久结论。
4. 定义并实现真正的 `browser_rendered` 执行引擎，只对合规且无需验证码的来源开放。
5. 用 Beauty Independent 做 `reference/metadata` canary；再分别验证 Cosmetics & Toiletries、Beauty Packaging、HAPPI。
6. Byrdie、未来迹、蝉妈妈继续停爬；刀法只做低频可用性监测。

## 不计入这 10 个的受限来源
